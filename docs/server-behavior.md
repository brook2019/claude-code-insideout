## Streaming Protocol Reference

Based on observed Server-Sent Events (SSE) from the Claude API:

```
Event Sequence (typical successful request):

1. message_start       → Message ID, model, role, usage (input tokens, cache stats)
2. content_block_start → thinking | text | tool_use (with id, name)
3. content_block_delta → thinking_delta | text_delta | input_json_delta
   (repeated for each chunk)
4. content_block_stop  → Block finalized
   (steps 2-4 repeat for each content block)
5. message_delta       → stop_reason, output usage (output_tokens)
6. message_stop        → Stream complete
```

### Key Observations

- **Token counts arrive in two phases**: input tokens at `message_start`, output tokens at `message_delta`
- **Cache stats are reported eagerly**: `cache_read_input_tokens` and `cache_creation_input_tokens` appear in `message_start.usage`
- **TTFT measures**: Time from request sent to first `message_start` event received
- **Multiple content blocks per message**: The server interleaves thinking, text, and tool_use blocks in a single response
- **Parallel tool_use**: Multiple `tool_use` content blocks can appear in one message (stop_reason = "tool_use")
- **Stop reasons observed**: `end_turn` (complete), `tool_use` (needs tool results), `max_tokens` (truncated)

## Rate Limiting (Observable Behavior)

- Rate limit information is communicated via HTTP response headers
- Claude Code implements exponential backoff with jitter on 429/529 responses
- Streaming idle timeout (configurable): aborts streams with no data for 90s
- Stall detection: logs gaps >30s between streaming events
